# Audit of the proposed desk and workshop interface

Reviewed September 5, 2026, after checkpoint `06fd0a5`. Scope: the supplied landing image, all five scenes in the second image, the attached design advice, and their mapping to the current app. This is a concept and capability review, not a claim that a static image proves usability.

## Decision

Keep the desk setting, prominent keyboard, restrained dark surfaces, contextual inspector and four task destinations: Build, Sound, Play and Discover. Do not implement the images literally. Several controls imply capabilities or measurements the app does not have, and the named example build contains a factual mismatch.

The entry flow will be **preview a featured build → customize it → Build / Sound / Play → share or export**. Returning users can resume their saved build directly. Discover holds the catalog, references and website import. These are destinations, not mandatory wizard steps.

The visual change should reduce the work needed to find a part, understand a change, hear the chosen recording and recover a previous state. Decorative detail earns its place by establishing scale, material and lighting without obscuring the keyboard or slowing interaction.

### Factual checks

- Mode's [Sonnet page](https://modedesigns.com/pages/sonnet) identifies it as a **75%** keyboard. Its [PCB compendium](https://compendium.modedesigns.com/parts/pcb-m75h-v2/) identifies the 75% PCB family and supported Sonnet revisions. The image's 65% label and Sixty Five PCB are not a valid specification to copy.
- Gateron's [Oil King listing](https://www.gateron.com/products/gateron-oil-king-pre-lubed-switches-linear) specifies 55 g operating force, 2 mm pre-travel and 4 mm total travel, with a different bottom-out force. A label simply saying “Weight 55g” loses that distinction. This check does not validate the image's unit price or sound descriptors.

## State and transition rules

1. A featured preview is not the working build. Starting customization produces one explicit undoable edit and keeps recovery available.
2. Build, Sound and Play share one current `Build`, one audio engine and one scene controller. Navigation does not reset selected parts or start sound unexpectedly.
3. Appearance, compatibility evidence, and the recording identity remain distinct. A dark keycap render cannot establish a GMK product, and a plate change cannot create a new recorded sound.
4. Inspecting a candidate does not silently apply it. Applying it updates the object, selection and fit result together.
5. All lower-level model interactions have an inspector/control equivalent. Typing mode gives typing priority; object inspection does not steal its keys.
6. Use real links/routes for destinations and reliable browser Back behavior. Transitions are interruptible; reduced motion removes camera travel and decorative parallax.
7. Narrow layouts put the object and active inspector in document flow, keep primary actions visible, and allow vertical touch scrolling.
8. Decorations share the scene's perspective and light, but not its interaction targets. Use reusable geometry, bounded texture/shadow costs and a static fallback when graphics fail.

## Verification needed before calling the change an improvement

- Preserve the existing behavior matrix above, including import errors, recording retry, storage denial and shared-build restoration.
- Run the same tasks before and after: choose a different case, change a palette, find a switch, play its available reference, type a test, undo, and share. Check whether navigation steps decrease or at least remain predictable. No user-study success rate is claimed yet.
- Use an independent verifier whose expectations are written before it sees the redesign. Test the rendered production candidate without showing the implementation or the implementer's results. Reconcile failures against the original expectation instead of editing tests to fit a screenshot.
- Verify desktop, 320/390px, touch, 200% zoom, keyboard-only operation, focus restoration, reduced motion, graphics failure, loading and empty states. Screen-reader output and contrast must be tested on the actual implementation, not inferred from the artwork.
- Verify a selected featured build produces its matching appearance/parts, previewing does not overwrite work, and navigating all four destinations preserves the build.
- Verify the volume control changes actual output gain, muted playback stays silent, above-unity gain is bounded, and existing build files/links still restore.
- No fake price, account, room, acoustic, bookmark, layer or comparison controls may pass review merely because they look like the reference.
